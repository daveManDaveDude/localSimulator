## Version-specific launcher evidence

Use the official [CPython v3.13.7 `PC/venvlauncher.c`](https://github.com/python/cpython/blob/v3.13.7/PC/venvlauncher.c), with the [same tagged raw source](https://raw.githubusercontent.com/python/cpython/v3.13.7/PC/venvlauncher.c). Its configuration helpers locate `pyvenv.cfg`, read `home` and select the original executable. `smuggle_path` sets `__PYVENV_LAUNCHER__`; `process` retains the original command line. `launch` creates a separate interpreter process, waits for it and returns its exit code. It also creates a Job with kill-on-close and silent-breakaway flags. Thus the launcher handle/PID is not automatically the script interpreter's identity. These claims concern the tagged source, not a runtime census.

Local prior static evidence identifies the venv executable as byte-identical to installed `venvlauncher.exe`; `pyvenv.cfg` names `C:\Python313`. The expected chain is wrapper → venv launcher → base interpreter executing supervisor, repeated when the supervisor launches a Python helper. Python-level executable naming alone does not identify the native process image. This explains why direct-parent/PID equality in review 15 cannot be assumed. Actual native identities and nested membership still require separately authorized observation.

### Exact-chain protocol

The immutable reviewed code/manifest and parent-owned one-use handoff establish allowed scripts, images and modes. W creates the fixed launcher suspended, assigns it to its outer Job and records launcher PID/creation identity in the handoff **before resume**. The actual supervisor's first script actions authenticate that record: its current native image equals the bound base executable; its parent is the recorded live launcher with matching creation time/image/hash; that launcher's parent is the recorded W process with matching creation identity. Verify the expected fixed command/script/mode evidence; no “any Python descendant” fallback. Keep identities distinct even when launcher exit forwards interpreter exit.

For P and H, S similarly records a suspended launcher identity in a fixed internal authorization. The executing helper authenticates its exact launcher → supervisor interpreter ancestry and its own native identity, then supplies a nonce-bound script-start record containing its PID/creation/image and associated launcher PID. S validates that executing process is contained in the owned inner Job before accepting identity/preflight PASS. Any additional unexpected launcher/interpreter depth fails closed. H's spawned child reports its actual script identity and the launched child handle separately; root/child assertions must not equate `Popen.pid` with the child script's `os.getpid()`.

Use bounded live ancestry/native-image queries and creation times to reject PID reuse; retain handles where practical. Authenticate membership with the parent's own Job census/IsProcessInJob checks, not a worker's unsupported assertion. A record from a trusted, hash-bound worker can initiate validation but cannot substitute for it. Parent-issued handoffs contain nonce, fixed mode, original manifest pins and exact allowed chain; consume once after validation using mode-specific names. Direct P invocation without a matching parent invocation/authorization fails.
