## B — what can and cannot be established within the current boundary

W can hash every file listed in the existing manifests before launching S. It can also refuse unsupported configurations before launch. It presently does neither a complete inventory comparison of reachable sources nor a complete model of their discovery. `Assert-ApprovedSearchPath` at 182–193 proves containment only. Binding a directory is not binding its current children; binding `sitecustomize.py` does not bind a package alternative, bytecode alternative or its imports.

A finite conservative audit would have to determine both S's and P's effective search/startup contexts before either interpreter runs: script directory, working directory when searched, PYTHONPATH including archives, venv/base standard-library/DLL/zip paths, actual site enablement and user-site policy, registry/other interpreter path configuration, `.pth` additions, and customization modules/packages. It must inventory and match executable files/cache/archive bytes in every effective location, rather than only a few hook names. Existing or sourceless `.pyc`, package initializers, extension modules, DLLs and transitive import paths all matter. Unknown/unsupported import finders, executable `.pth`, archive forms, path overrides or startup configurations must be refused. Missing optional locations must be positively characterized as absent, not omitted after an enumeration error.

That audit can close a **specified finite supported search profile**, at the observation instant. It cannot establish the task's unrestricted promise about *every executable source* merely because arbitrary bound Python/native code starts from those locations. A customization module, package initializer, import hook or extension may subsequently change `sys.path`, install a finder, add a DLL directory, load a resource/native library by a computed path, or execute generated/in-memory code. Native dependency discovery and Windows loader resolution are not equivalent to PYTHONPATH/PATH directory membership. Hashing all initial directories still does not constrain those later choices. A post-import strict census is useful evidence but cannot repair execution of an unbound source. The same problem starts before S, so another P validator or S helper cannot bootstrap the missing guarantee.

The smallest boundary decision is therefore an **explicit acceptance/trust-boundary decision**, not permission for another guessed path scan: define whether the approved exact interpreter/OS loader and reviewed frozen package/bootstrap code are trusted to implement a finite, enumerated search profile. Under that narrower, concrete contract W could conservatively bind all on-disk executable/cache/archive candidates in that profile, refuse every unmodelled hook/path/loader configuration, and retain later census/revalidation. Existing schemas can hold file bindings, but current allowed roots alone do not define this trust/profile contract. This requires an amended accepted requirement before implementation; this diagnosis does not silently grant it or call it equivalent to universal prevention.

If the user requires prevention for every dynamically selected executable source, rather than that explicit trusted-code/profile boundary, the minimum *technical* boundary must instead permit enforced import/native-load confinement or a controlled execution environment. That necessarily relaxes the present command/environment/implementation constraints; merely adding `-I` or `-S` is insufficient to constrain arbitrary native loads and is not an approved fix here. Selecting such an architecture needs a separate bounded design, not Luna cycle 2 under this plan. No new runtime discovery phase or expanded manifest schema is recommended as a substitute: discovery alone does not enforce confinement.
